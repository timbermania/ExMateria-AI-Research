# Event End Opcode

FFT's two event-script terminators: `{DB}` Event End and `{E3}` Event End 2 — which **share one handler body** at `0x801442BC` — the dispatcher is a compare chain whose delay slots load the *next* constant, so `ram:801442AC beq s4,v0` against `v0 = 0xDB` and `ram:801442B4 bne s4,v0` against `v0 = 0xE3` both arrive at the same body (corrected 2026-08-21; the restore-pass body at `0x8014429C` previously attributed to `{DB}` is opcode `{12}`) and `{E3}` Event End 2 (hard end — synchronous quiesce: barrier on the pending screen/transition flag, drain of kind-8 block child tasks, unit-state finalization, then an explicit fiber mark-complete). Both are RE'd byte-exact against live RAM on the `orbonne_darkscreen_dispatch.sstate` anchor (2026-07-02 session 3), and both are ported in the `godot-learning` `ScenarioVM` as clean context terminators — no unhandled-opcode halt warning — replacing the false "stopping at unhandled opcode 'Event End'" halt every scenario tail previously produced.

## Points

- **`{DB}` Event End is a per-unit graphic/palette-restore pass, not a fiber stop: case `0x8014429c` (operand size 0) calls `FUN_80147d98`, which walks the 21 active roster slots, reads each unit's event-id byte `+0x161` and flag `+0x5 & 0x30`, and for slots whose event id matches (a0 = sign-extended low16 of s3) calls `FUN_8008d26c(slot, 2, −0x1F, −0x1F)` — a graphic/palette revert (the `∓0x1F` curve-index convention matches the prayer-darkening palette path) — then the interpreter just loops back to fetch; the fiber actually terminates when the chunk's trailing unhandled byte falls through to the default `event_fiber_mark_complete` @ `0x80145f3c`.** — `[S·D·R] 3/3`

  - D: live dispatch of `{DB}` captured as the first opcode of the battle-intro chunk after the scenario-4 event closes (opcode stream `… {1C}@822 {DB}@0 {F2}@1 …`, resume of `orbonne_darkscreen_dispatch.sstate`, 2026-07-02)

  - ⚠ SUPERSEDED (2026-08-21) by: **two errors, one of attribution and one of behaviour.** (a) The restore pass at `0x8014429C` is **not `{DB}`** — it is opcode **`{12}`**, which this vault's own catalog still lists as "no confirmed behavior" (see [[Event Opcode Catalog]]). The dispatcher is a compare chain, not a jump table, and each test's delay slot loads the *next* constant: `0x80144290 bne s4,v0 -> 0x801442AC` runs against the `ori v0,zero,0x12` at `ram:80144254`, so `0x8014429C` is the fall-through for opcode `0x12`. Everything this point says about the pass itself is right and now belongs to `{12}` — including the `sll`/`sra` pair at `ram:80144298`/`ram:801442A0` giving `a0 = sign-extended low16 of s3`. (b) `{DB}` **chains rather than ends**: `0x801442AC beq s4,v0 -> 0x801442BC` with `v0 = 0xDB` (loaded in the preceding delay slot at `ram:80144294`) routes `{DB}` into the **same body as `{E3}`**, whose tail at `ram:80144368` reads event variable `0x27`, and — unless the id is `429`, `465`, `0` or in `400..425` — calls `LoadNextEvent` at `ram:801443F0` and, on a non-zero return, `bne v0,zero -> 80143CDC` back to the top of the interpreter against the newly loaded script. So a scene chains by writing its successor's id into variable `0x27` before it ends; there is no separate chaining mechanism. Re-derived instruction by instruction off `project-assets/fft-extract/BATTLE.BIN` (RAM = file offset + `0x80067000`); the special-id set, the `0x8004E5D0` per-event halfword table and its `0xF300` mask all read exactly as reported. web-psx measured it dynamically: warping to event 2 loads slots **2, 4, 5** in sequence off one entry to the event task. **Cost of the superseded reading:** a port that closes the event context at `{DB}` plays 1 scene where the console plays 3 — it looks like the scripts are short rather than like the interpreter is wrong. Note this vault's `godot-learning` mirror does exactly that (`_op_event_end` sets `ctx.alive = false` for both `0xDB` and `0xE3`), so the `R` evidence on this point validated the wrong behaviour (ExMateria-AI-Research#5)
- **`{E3}` Event End 2 is the hard terminator + battle handoff used by the ~37 battle-intro chunks that hand the event straight to battle setup: case `0x801442bc` (operand size 0) takes the `FUN_801460a4` barrier (spin `event_fiber_yield` while `*0x8016606c != 0` — the pending screen/transition flag), drains kind-8 (block) child tasks via `FUN_80149cbc(0x8)`, runs the unit-state finalization loop, then fires an explicit `event_fiber_mark_complete` @ `0x80144484` — everything is quiesced synchronously before the hard stop.** — `[S·D·R] 3/3`
  - S: case `0x801442bc`, barrier `FUN_801460a4` @ `0x801460a4` / flag `0x8016606c`, kind-8 drain `FUN_80149cbc(0x8)`, explicit stop `0x80144484` (`battle_disassembly.txt`)
