# Dialogue Font Palette

The `{10}` Display Message font-palette mechanism, settled by static + dynamic analysis (2026-06-27): the only palette input is the `{Color NN}` string opcode `0xE3` — the handler's message walk latches it into `DAT_8016dae2` and passes it to the 2bpp→4bpp glyph rasterizer `FUN_8014bd88 @ 0x8014BD88`, where `final_index = glyph_pixel(1..3) + {Color NN}` is an additive offset into a 16-color dialog CLUT (`{Color 00}` default = slots 1–3 body, `{Color 08}` = slots 9–11 speaker name). Box type (`Dialog & 0x70`) drives box geometry/anchoring only and never touches the glyph CLUT. Which 16-color row a glyph actually samples is decided by the primitive's CLUT id, and all 22 FRAME.BIN palettes are resident in VRAM simultaneously (pal 0–15 at X=960 rows 496–511, pal 16–21 at X=976 rows 506–511): the chapel prayer (`Dialog=0x09`) carries CLUT id `0x7cbc` = VRAM (960,498) = FRAME pal 2 (off-white ramp) while the boxed dialog's glyphs carry `0x7c3c` = VRAM (960,496) = FRAME pal 0 (dark body (49,41,32), red speaker (106,41,16)) — the box path never takes the conditional `0x7cbc` store @ `0x80130FFC`, and the prayer renders through a separate pre-rasterized path that skips the rasterizer + `GsLoadImage` upload, so box body ≠ prayer body — a 2026-06-27 re-investigation (`handoff_dialog_box_palette_WRONG_refind.md`) contests this settled model, claiming VRAM (960,498) is a per-context compose slot the `{10}` box handler writes via `0x7cbc` with the box composing the pal 0/15 family there; both readings agree the box's palette content is the pal 0/15 dark-body + red-speaker family and the prayer's is pal 2, and the box's CLUT row (496/`0x7c3c` vs 498/`0x7cbc`) is CONTESTED pending a dump from an actual box frame. `godot-learning` implements the box with a 3-level nearest-neighbor CUSTOM shader remap to the dumped CLUT (`DialogueBox` + `ui_font_char.gdshader`) and the prayer/menu text with the baked off-white atlas (FRAME pal 2). The `UIChar` glyph shader tints by multiplying atlas colour × `font_color` (darken-only; the prayer overlay's white `_container.modulate` is the atlas-native reference); the comma's question-mark fallback was closed 2026-06-27 when `CHAR_TO_INDEX_RENDER` added the multi-byte-only glyphs (comma = index 2196) to the baked render charmap, so the comma now renders as a real comma. A 2026-06-27 handoff pins two overlay-side facts: the `{Color NN}` sink (`typewriter_set_palette` → the `palette` member) is a dead write on the overlay path, and the post-refactor "prayer palette looks wrong" report was a stale, gitignored, locally derived `font_atlas.tga` (2026-06-22 bake, predating the real-palette commit `954a24b2`), fixed by the 2026-06-27 atlas regen.
